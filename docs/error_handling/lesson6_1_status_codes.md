課題に取り組む前に、リモートの全てのブランチを取得してから、Lesson 用のブランチに切り替えしてください：

```bash

git checkout main

# 最新の状態に更新（重要：必ずpullすること）
# Lesson用のブランチに切り替え（リモートのブランチを追跡）
```

**推奨：** 各 Lesson ごとに専用のブランチで作業することで、作業を整理しやすくなります。

### データベースの準備

データベースを初期状態に戻してください：

```bash
sail artisan migrate:refresh --seed
```

### フロントエンドの再起動

Vite の開発サーバーを再起動してください：

```bash
# Ctrl+Cで現在のプロセスを停止してから
sail npm run dev
```

### ログ設定の確認

`.env`ファイルで、ログチャンネルが`daily`になっていることを確認してください：

```
LOG_CHANNEL=daily
```

## 🚦 第 3 章：ステータスコードの大分類

### 🎭 百の位に意味がある

**👩‍💻 ユーザー：** 「200 とか 404 とか 500 とか...たくさんあるんですか？」

**🐘 ガネーシャ：** 「結構あるで。でもな、**百の位を見れば大体分かる**ようになっとる」

```
┌────────────────────────────────────────────────────────┐
│           ステータスコードの大分類                      │
├────────────────────────────────────────────────────────┤
│                                                        │
│  🚦 信号機に例えると分かりやすいで！                   │
│                                                        │
│  ┌─────────────────────────────────────────────────┐  │
│  │                                                 │  │
│  │   🟢 2xx = 青信号                               │  │
│  │      「成功！進んでOK！」                        │  │
│  │                                                 │  │
│  │   🟡 3xx = 黄信号                               │  │
│  │      「こっちじゃなくてあっち見て」             │  │
│  │      （リダイレクト、今回は省略）               │  │
│  │                                                 │  │
│  │   🔴 4xx = 赤信号（お客さんのミス）             │  │
│  │      「あなたのリクエストがおかしいよ」         │  │
│  │                                                 │  │
│  │   🔴 5xx = 赤信号（お店のミス）                 │  │
│  │      「こっち（サーバー）が悪い、ごめん」       │  │
│  │                                                 │  │
│  └─────────────────────────────────────────────────┘  │
│                                                        │
└────────────────────────────────────────────────────────┘
```

**👩‍💻 ユーザー：** 「4xx と 5xx の違いは『誰のミスか』ってことですか！」

**🐘 ガネーシャ：** 「そう！めっちゃ大事なポイントや！」

### 🏪 コンビニで例えてみよう

| おにぎり買えた         | -          | 🟢 2xx（成功）   |
| 存在しない商品を頼んだ | お客さん   | 🔴 4xx           |

**👩‍💻 ユーザー：** 「分かりやすい！お客さんのミスか、お店のミスか、ってことですね」

**🐘 ガネーシャ：** 「せや！これが分かれば、ステータスコードの半分は理解したようなもんや！さすガネーシャの教え子！」

### 🟢 成功系（2xx）

#### 200 OK 「成功したで！」

```
🏪 コンビニの例
──────────────────────────────────
👩‍💻「おにぎり1個ください」
🏪「はい、どうぞ！」
→ 200 OK ✅
```

```
💻 APIの例
──────────────────────────────────
リクエスト：GET /api/tasks/1

レスポンス：200 OK
{
  "id": 1,
  "title": "買い物に行く",
  "status": "todo"
}
```

**🐘 ガネーシャ：** 「一番基本のやつや。『ちゃんとできたよ』って意味」

---

#### 201 Created 「作ったで！」

```
🏪 コンビニの例
──────────────────────────────────
👩‍💻「新規会員登録したいです」
🏪「はい、登録完了しました！会員番号は12345です」
→ 201 Created ✅
```

```
💻 APIの例
──────────────────────────────────
リクエスト：POST /api/tasks
{
  "title": "新しいタスク"
}

レスポンス：201 Created
{
  "id": 42,
  "title": "新しいタスク",
  "status": "todo"
}
```

**👩‍💻 ユーザー：** 「200 と 201 の違いは何ですか？」

**🐘 ガネーシャ：** 「200 は『取得とか更新が成功した』、201 は『新しく作った』って違いや」

```
┌───────────────────────────────────────┐
│  200 vs 201 の使い分け                │
├───────────────────────────────────────┤
│                                       │
│  200 OK                               │
│  → GET（取得）が成功                  │
│  → PUT/PATCH（更新）が成功            │
│                                       │
│  201 Created                          │
│  → POST（新規作成）が成功             │
│                                       │
└───────────────────────────────────────┘
```

```
┌─────────────────────────────────────────────────────┐
│           401 vs 403 の違い                         │
├─────────────────────────────────────────────────────┤
│                                                     │
│  🔐 401 Unauthorized                                │
│  ────────────────────                               │
│  「そもそも誰か分からん」                           │
```

#### 409 Conflict 「ルール的にアカンで」

```
🏪 コンビニの例
──────────────────────────────────
👩‍💻「この商品返品したいです」
🏪「レシートは？」
👩‍💻「これです」（3ヶ月前の）
🏪「返品期限は1週間以内です。お受けできません」
→ 409 Conflict ❌
```

```
💻 APIの例
──────────────────────────────────
リクエスト：POST /api/tasks/1/start
（ステータスが「done」のタスクを開始しようとした）

レスポンス：409 Conflict
{
  "message": "完了済みのタスクは開始できません"
}
```

**👩‍💻 ユーザー：** 「これはどういう時に使うんですか？」

**🐘 ガネーシャ：** 「ビジネスルール違反の時や。例えば...」

```
┌─────────────────────────────────────────────────────┐
│           409 Conflict を使う場面                   │
├─────────────────────────────────────────────────────┤
│                                                     │
│  ・完了済みタスクを再度完了しようとした             │
│  ・すでに存在するメールアドレスで登録しようとした   │
│  ・キャンセル済みの注文をキャンセルしようとした     │
│  ・削除済みのデータを更新しようとした               │
│                                                     │
│  → データは存在する（404じゃない）                  │
│  → 権限もある（403じゃない）                        │
│  → でもビジネスルール的にダメ！                     │
│                                                     │
└─────────────────────────────────────────────────────┘
```

### 🔴 サーバーエラー系（5xx）

#### 500 Internal Server Error 「こっちがバグった...」

```
🏪 コンビニの例
──────────────────────────────────
👩‍💻「おにぎりください」
🏪「かしこまりまし...」
💥 レジが爆発
🏪「すみません、機械が壊れました...」
→ 500 Internal Server Error ❌
```

```
💻 APIの例
──────────────────────────────────
リクエスト：GET /api/tasks

（サーバー側でデータベース接続エラーが発生）

レスポンス：500 Internal Server Error
{
  "message": "サーバーエラーが発生しました"
```

#### 😱 地獄のシナリオ 1：何が悪いか分からない

```php
// ❌ エラーハンドリングしてない
public function show($id)
{
    $task = Task::find($id);
    return response()->json($task);
}
```

```
何が起こる？

レスポンス：200 OK ← えっ！？
```

**👩‍💻 ユーザー：** 「200 って成功じゃないんですか！？」

**🐘 ガネーシャ：** 「そう！存在しない ID なのに 200 が返ってきてる。これじゃフロントエンド側で『成功したのに中身が無い...なんで？』ってなるやろ？」

**正しくは：**

```php
// ✅ エラーハンドリングしてる
public function show($id)
{
    $task = Task::find($id);

    if (!$task) {
        return response()->json([
            'message' => 'タスクが見つかりません'
        ], 404);  // ← 適切なステータスコード！
    }

    return response()->json($task);
}
```

#### 😱 地獄のシナリオ 2：何でも 500

```php
// ❌ とりあえず500
public function destroy($id)
{
    $task = Task::find($id);

    if (!$task) {
        return response()->json(['error' => 'NG'], 500);
    }

    if ($task->status === 'done') {
        return response()->json(['error' => 'NG'], 500);
    }

    $task->delete();
    return response()->json(['message' => 'OK']);
}
```

```
何が起こる？

→ 500 Server Error
👩‍💻ユーザー：「サーバーがバグった！？私のせいじゃないよね？」

シナリオB：完了済みタスクを削除しようとした
→ 500 Server Error
👩‍💻ユーザー：「また500...何が悪いの！？」
```

**🐘 ガネーシャ：** 「全部 500 にしたら、ユーザーのミスなのかサーバーのミスなのか分からんのや」

**正しくは：**

```php
// ✅ 適切なコードを返す
public function destroy($id)
{
    $task = Task::find($id);

    if (!$task) {
        return response()->json([
            'message' => 'タスクが見つかりません'
        ], 404);  // ← 存在しないから404
    }

    if ($task->status === 'done') {
        return response()->json([
            'message' => '完了済みタスクは削除できません'
        ], 409);  // ← ビジネスルール違反だから409
    }

    $task->delete();
    return response()->json(['message' => '削除しました']);
}
```

## 📝 第 7 章：エラーハンドリングのまとめ

**🐘 ガネーシャ：** 「さて、長くなったけどまとめるで！」

### ✅ エラーハンドリングの 3 原則

```
┌─────────────────────────────────────────────────────┐
│           エラーハンドリング3原則                    │
├─────────────────────────────────────────────────────┤
│                                                     │
│  1️⃣ 適切なステータスコードを返す                    │
│     → 4xx = ユーザーのミス                          │
│     → 5xx = サーバーのミス                          │
│                                                     │
│  2️⃣ 分かりやすいメッセージを返す                    │
│     → 「何が」「なぜ」ダメなのか                    │
│                                                     │
│  3️⃣ エラーを握りつぶさない                          │
│     → 失敗したのに200を返さない                     │
│     → try-catchで何もしない、をしない               │
│                                                     │
└─────────────────────────────────────────────────────┘
```

---

### 🎯 よくある状況とステータスコード

| 状況                         | ステータスコード          |
| ---------------------------- | ------------------------- |
| データの取得・更新に成功した | 200 OK                    |
| データを新規作成した         | 201 Created               |
| ログインしていない           | 401 Unauthorized          |
| 権限がない                   | 403 Forbidden             |
| データが存在しない           | 404 Not Found             |
| ビジネスルール違反           | 409 Conflict              |
| バリデーションエラー         | 422 Unprocessable Entity  |
| サーバー側のバグ             | 500 Internal Server Error |
