## 📖 第1章：手動テストと自動テストの違い

### 🎭 まずは「テスト」の意味から

**🐘ガネーシャ：** 「そもそも『テスト』って何やと思う？」

**👩‍💻ユーザー：** 「えっと...動くか確認すること...ですか？」

**🐘ガネーシャ：** 「せや！もうちょい正確に言うと『**期待通りに動くか確認すること**』やな」

```
┌─────────────────────────────────────────────────────────────┐
│                    テストとは？                              │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│   「この入力をしたら、この出力が返ってくるはず」            │
│                                                             │
│       ↓ 実際にやってみる                                    │
│                                                             │
│   「期待通りだった！」 → ✅ テスト成功                      │
│   「違った！」        → ❌ テスト失敗（バグ発見）           │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

**👩‍💻ユーザー：** 「なるほど、それを私は Postman で手動でやってたってことですね」

**🐘ガネーシャ：** 「せや。それが『**手動テスト**』や。ほな『**自動テスト**』は何やと思う？」

**👩‍💻ユーザー：** 「えっと...自動で...やる？」

**🐘ガネーシャ：** 「正解！**『テストをコードで書いて、コンピュータに実行させる』**のが自動テストや」

### 📊 手動テスト vs 自動テスト

```
┌─────────────────────────────────────────────────────────────┐
│                 手動テスト vs 自動テスト                     │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│  【手動テスト】                【自動テスト】               │
│                                                             │
│  👩‍💻 人間が画面やPostmanで実行   🤖 コンピュータが実行        │
│  ⏱️ 1回3分 × 15個 = 45分      ⏱️ 全部で30秒               │
│  😫 毎回やるの面倒            🔄 何度でも一瞬              │
│  👀 見落としあり              ✅ 必ず同じチェック           │
│  📝 手順書が必要              📝 テストコード自体が手順書   │
│  🔑 毎回トークン設定          🔑 自動でログイン状態に       │
│  📊 目でJSON確認              📊 自動で値をチェック         │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

**👩‍💻ユーザー：** 「30秒で全部確認できるんですか！？」

**🐘ガネーシャ：** 「せや。しかもコマンド1つでな」

```bash
# これだけで全テスト実行
sail artisan test
```

**👩‍💻ユーザー：** 「えっ、これだけ...？Postman 開いて、トークン設定して、URL 入力して...って作業が全部いらない...？」

**🐘ガネーシャ：** 「せや！しかも**夜中に自動で実行**することもできるんやで」

---

### 🔄 具体的に何が変わる？

**🐘ガネーシャ：** 「お前がやっとった作業がどう変わるか見せたるわ」

```
┌─────────────────────────────────────────────────────────────┐
│         今までの手動テスト → 自動テストに置き換え            │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│  【今まで：Postman で手動確認】                              │
│                                                             │
│  1. Postman 起動                                            │
│  2. POST /api/login でトークン取得                          │
│  3. トークンをコピーして Headers に設定                     │
│  4. GET /api/projects を実行                                │
│  5. ステータスコードが 200 か目で確認                       │
│  6. JSON の中身を目で確認                                   │
│  7. 次の API へ...（繰り返し）                              │
│                                                             │
│  【これから：自動テスト】                                   │
│                                                             │
│  $response = $this->actingAs($user)    // ← 自動ログイン   │
│      ->getJson('/api/projects');       // ← 自動リクエスト │
│                                                             │
│  $response->assertStatus(200);         // ← 自動で確認     │
│  $response->assertJsonCount(1, 'data');// ← 自動で確認     │
│                                                             │
│  → 人間がやることは「php artisan test」を実行するだけ！    │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

**👩‍💻ユーザー：** 「`actingAs($user)` でログイン状態になる...！トークンのコピペがいらない...！」

**🐘ガネーシャ：** 「せやろ？しかも `assertStatus(200)` で**自動的に**ステータスコードを確認してくれる。目で見る必要がないんや」

## 📖 第2章：なぜ自動テストが必要なのか

**👩‍💻ユーザー：** 「大変そう...」

**🐘ガネーシャ：** 「せや。ある日エジソンくんがワシに泣きついてきてな」

```

エジソン：「ガネーシャ先生！1000回目の実験で光ったのに、

```

**👩‍💻ユーザー：** 「あ、それってテストコードと同じ...！」

**🐘ガネーシャ：** 「さすがやな！**テストコードは『いつでも同じ条件で再現できる実験手順書』**なんや」

### 📊 自動テストの3大メリット

**🐘ガネーシャ：** 「自動テストのメリットをまとめるとこうや」

```
┌─────────────────────────────────────────────────────────────┐
│                  🔍 自動テストの3大メリット                  │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│  1️⃣  バグを早期発見できる                                   │
│      → コードを変更した時、すぐに問題に気づける             │
│      → 本番リリース前に「壊れてる！」と分かる               │
│                                                             │
│  2️⃣  安心してリファクタリングできる                         │
│      → 動作が保証されているので、改善しやすい               │
│      → 「直したら他が壊れた」を防げる                       │
│                                                             │
│  3️⃣  ドキュメントとしても機能する                           │
│      → テストコードが「仕様」を示してくれる                 │
│      → 「このAPIは何を返すべきか」がコードで分かる          │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

**👩‍💻ユーザー：** 「3番目の『ドキュメント』ってどういう意味ですか？」

**🐘ガネーシャ：** 「ええ質問や！例えばこのテストコードを見てみ」

```php
public function test_can_create_project(): void
{
    // ユーザーがログインして
    $user = User::factory()->create();
    
    // プロジェクトを作成すると
    $response = $this->actingAs($user)
        ->postJson('/api/projects', [
            'name' => 'テストプロジェクト',
        ]);

    // 201が返って、nameが含まれる
    $response->assertStatus(201);
    $response->assertJson([
        'name' => 'テストプロジェクト',
    ]);
}
```

**👩‍💻ユーザー：** 「あ！これ読むだけで『プロジェクト作成APIはnameを送ると201が返る』って分かりますね！」

**🐘ガネーシャ：** 「せやろ？しかもこのドキュメント、**絶対に古くならへん**んや」

**👩‍💻ユーザー：** 「え、どういうことですか？」

**🐘ガネーシャ：** 「普通のドキュメントは更新し忘れるやろ？でもテストは**コードが変わったら失敗する**。失敗したらテストも直さなアカン。だから常に最新なんや」

**👩‍💻ユーザー：** 「なるほど！テストが通ってる = ドキュメントが正しいってことか！」

```
┌─────────────────────────────────────────────────────────────┐

```

**👩‍💻ユーザー：** 「火曜日の時点で気づけるのは大きいですね...」

**🐘ガネーシャ：** 「せや。**バグは早く見つけるほど修正コストが低い**んや。本番で見つかったら大騒ぎやけど、開発中に見つかったら『あ、直そ』で済むやろ？」

## 📖 第5章：テストを書くタイミング

### 🤔 いつテストを書くべき？

**👩‍💻ユーザー：** 「テストの大切さは分かりました！でも、いつ書けばいいんですか？」

**🐘ガネーシャ：** 「ええ質問や。いくつかパターンがあるで」

```
┌─────────────────────────────────────────────────────────────┐
│                テストを書くタイミング                        │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│  1️⃣  実装した後に書く（最も一般的）                         │
│      → 機能を作る → テストを書く → 両方コミット            │
│                                                             │
│  2️⃣  実装する前に書く（TDD: テスト駆動開発）                │
│      → テストを書く → テストが通るように実装する           │
│      → 上級者向け                                           │
│                                                             │
│  3️⃣  バグを直す時に書く                                     │
│      → バグを再現するテストを書く → バグを直す             │
│      → 同じバグが二度と起きないようにする                  │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

**👩‍💻ユーザー：** 「最初は1番目の『実装した後に書く』でいいですか？」

**🐘ガネーシャ：** 「せや！まずはそれでええ。**完璧を目指さず、1つずつテストを増やしていく**のが大事や」
