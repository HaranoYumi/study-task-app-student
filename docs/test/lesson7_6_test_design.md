## 📖 第1章：テストの目的を思い出そう

### 🎭 そもそも何のためにテストを書くのか

**🐘ガネーシャ：** 「まず、テストの目的を思い出してみ」

**👩‍💻ユーザー：** 「えっと...バグを見つけるため？」

```
┌─────────────────────────────────────────────────────────────┐
│                   テストの目的                               │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│  1️⃣  重要な機能が壊れていないことを確認する                 │
│      → 「ログインできなくなった」は致命的                  │
│                                                             │
│  2️⃣  ビジネスルールが守られていることを確認する             │
│      → 「todo から直接 done になった」は業務ルール違反      │
│                                                             │

│      → 「他人のデータが見えた」は大問題                     │
│                                                             │
│  4️⃣  リグレッション（退行）を防ぐ                           │

## 📖 第2章：テストの優先度の考え方

### 🎭 優先度の高いテスト

**🐘ガネーシャ：** 「テストの優先度を考える時、こう考えるとええで」

```
┌─────────────────────────────────────────────────────────────┐
│               テストの優先度ピラミッド                       │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│                        ▲                                    │
│                       /＼                                   │
│                      /  ＼                                  │
│                     / 低  ＼  ← 細かいUI、見た目           │
│                    /────────＼                              │
│                   /    中     ＼ ← バリデーション          │
│                  /──────────────＼                          │
│                 /       高        ＼ ← ビジネスロジック    │
│                /────────────────────＼                      │
│               /        最高          ＼ ← 認証・認可        │
│              ──────────────────────────                    │
│                                                             │
│  【最高】認証・認可（セキュリティ）                         │
│    → 他人のデータが見えたら大問題                          │
│                                                             │
│  【高】ビジネスロジック（業務ルール）                       │
│    → お金や重要なステータスに関わる処理                    │
│                                                             │
│  【中】バリデーション（入力チェック）                       │
│    → 不正なデータが入るのを防ぐ                            │
│                                                             │
│  【低】細かいUI、見た目                                     │
│    → 後回しでもOK                                          │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

┌─────────────────────────────────────────────────────────────┐
│           タスク管理アプリのテスト優先度                     │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│  【最高優先度】必ずテストする                               │
│    ✅ ログインしてない人はアクセスできない（401）          │
│    ✅ 他人のプロジェクトにアクセスできない（403）          │
│    ✅ メンバーでない人はタスクを見れない（403）            │
│                                                             │
│  【高優先度】できるだけテストする                           │
│    ✅ タスクの状態遷移（todo→doing→done）                  │
│    ✅ 完了タスクは編集できない                              │
│    ✅ 最後のオーナーは削除できない                          │
│                                                             │
│  【中優先度】余裕があればテストする                         │
│    ✅ 名前が空だとエラー                                    │
│    ✅ 名前が長すぎるとエラー                                │
│                                                             │
│  【低優先度】後回しでもOK                                   │
│    ⚠️ レスポンスの日付フォーマット                         │
│    ⚠️ ソート順                                              │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

**👩‍💻ユーザー：** 「セキュリティ関連が一番大事なんですね！」

**🐘ガネーシャ：** 「せや。**他人のデータが見えるバグ**と**日付のフォーマットが違うバグ**、どっちが致命的か考えたら分かるやろ？」

## 📖 第3章：テストケースの洗い出し方

### 🎭 「正常系」と「異常系」で分ける

**🐘ガネーシャ：** 「テストケースを考える時は、まず**正常系**と**異常系**に分けるんや」

```
┌─────────────────────────────────────────────────────────────┐
│            テストケースの洗い出し方（基本）                  │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│  【ステップ1】正常系を考える                                │
│    「この機能が成功するケースは？」                         │
│                                                             │
│  【ステップ2】異常系を考える                                │
│    「この機能が失敗するケースは？」                         │
│    → 認証エラー（401）                                     │
│    → 権限エラー（403）                                     │
│    → 存在しない（404）                                     │
│    → ビジネスルール違反（409）                             │
│    → バリデーションエラー（422）                           │
│                                                             │
│  【ステップ3】境界値を考える                                │
│    「ギリギリのケースは？」                                 │
│    → 255文字OK、256文字NG                                  │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

## 📖 第4章：テストを書く時のコツ

### 🎭 1つのテストで1つのことを検証する

**🐘ガネーシャ：** 「テストを書く時の大事なコツを教えるで」

```
┌─────────────────────────────────────────────────────────────┐
│                テストを書く時のコツ                          │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│  1️⃣  1つのテストで1つのことを検証する                       │
│      → テストが失敗した時、原因が分かりやすい              │
│                                                             │
│  2️⃣  テスト名で何をテストしているか分かるようにする         │
│      → test_can_create_project                             │
│      → test_cannot_start_done_task                         │
│                                                             │
│  3️⃣  AAA パターンを守る                                     │
│      → Arrange（準備）→ Act（実行）→ Assert（検証）       │
│                                                             │
│  4️⃣  テスト同士を独立させる                                 │
│      → 他のテストの結果に依存しない                        │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

---

### ❌ 悪い例と ✅ 良い例

**🐘ガネーシャ：** 「具体的に見てみよか」

```php
// ❌ 悪い例：1つのテストで複数のことを検証
public function test_プロジェクトのCRUD操作(): void
{
    $user = User::factory()->create();
    
    // 作成
    $response = $this->actingAs($user)->postJson('/api/projects', ['name' => 'テスト']);
    $response->assertStatus(201);
    
    // 取得
    $response = $this->actingAs($user)->getJson('/api/projects');
    $response->assertStatus(200);
    
    // 更新
    $response = $this->actingAs($user)->putJson('/api/projects/1', ['name' => '更新']);
    $response->assertStatus(200);
    
    // 削除
    $response = $this->actingAs($user)->deleteJson('/api/projects/1');
    $response->assertStatus(200);
}
// → 失敗した時、どの操作で失敗したか分かりにくい！
```

```php
// ✅ 良い例：1つのテストで1つのことを検証
public function test_プロジェクトを作成できる(): void
{
    $user = User::factory()->create();
    
    $response = $this->actingAs($user)
        ->postJson('/api/projects', ['name' => 'テスト']);
    
    $response->assertStatus(201);
}

public function test_プロジェクト一覧を取得できる(): void
{
    // ...
}

public function test_プロジェクトを更新できる(): void
{
    // ...
}

public function test_プロジェクトを削除できる(): void
{
    // ...
}
// → 失敗した時、どの機能が壊れたか一目で分かる！
```
